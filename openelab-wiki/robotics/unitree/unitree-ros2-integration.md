## Product overview <a href="#product-overview" id="product-overview"></a>

`unitree_ros2` supplies ROS 2 message packages and examples for communicating with Unitree robots through Cyclone DDS. Its direct DDS approach does not require wrapping every message through the SDK2 application API. Integration nevertheless depends on the exact message family, robot software, DDS domain, network interface and middleware. A topic name alone is insufficient to select a decoder. This guide covers ROS 2 package/environment selection, message ownership, isolated source inspection and a conditional subscriber-only first hardware result. It does not supply robot commissioning or a general SDK2 installation tutorial. [Repository introduction and configuration](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/README.md)

The reviewed source is **`unitreerobotics/unitree_ros2` commit `668d1ec5a05d1c38d3306bdca7d59f2ba3581a88`**, commit date 2 July 2026. `version.txt` contains `0.3.0`, while the ROS package manifests contain `0.0.0`; neither value alone identifies the full wire contract. Use the commit and exact `.msg` files as the documentation baseline. The changelog's v0.3.0 entry predates this commit and announces breaking hand-message changes. ## Applications <a href="#applications" id="applications"></a>

* Inspect a ROS message contract before selecting a subscriber, especially when moving between a Go2-family state stream and G1/H1-2 messages.
* Prepare a Humble environment that builds only interface packages, so initial state acquisition does not require building or launching motion examples.
* Read an identified robot's status without creating an application publisher on command topics, once model, firmware and network prerequisites have been resolved.
* Compare isolated simulation data with real-robot topics while preserving separate domain/interface settings. A simulator publishing a message is not proof that robot firmware publishes it. [ROS 2 usage](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/README.md), [simulation behavior and configuration](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/readme.md)

The repository also contains high-level service clients and low-level motor examples. Their inclusion documents interfaces; it does not establish safe gains, actuator limits, supported maneuvers or correct mode transitions for the purchased robot.

### Message layout and ownership <a href="#message-layout-and-ownership" id="message-layout-and-ownership"></a>

The robot or simulator owns outgoing state samples; the application consumes them. For any future control session there must be one deliberately selected command owner and a model-specific handover procedure. A state subscription neither grants actuator authority nor disables another controller.

| Contract                               | Distinguishing fields / layout                                                                                                                                                                                                                                                               | Ownership and interpretation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `unitree_go/msg/LowState`              | Header/level/serial/version fields; IMU; `MotorState[20]`; BMS; four foot forces and estimates; tick; 40 remote bytes; power/fan fields; reserve and CRC.                                                                                                                                    | Robot → reader. Preserve raw fields and their types. Do not apply HG offsets or infer active joint count from array length. [GO schema](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/cyclonedds_ws/src/unitree/unitree_go/msg/LowState.msg)                                                                                                                                                                                                                                                                                                                     |

It does not contain GO's embedded BMS, foot-force or `power_v/power_a` fields. [HG schema](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/cyclonedds_ws/src/unitree/unitree_hg/msg/LowState.msg)                                                                                                                                                                                                                                                                                                                                                  |

Quaternion logs in the read examples use **w, x, y, z** order; RPY comments use ZYX/body-frame language. Do not copy those four values directly into ROS geometry message members without an explicit field mapping. `tick` has no verified period or epoch in the read ROS schema. GO's `TimeSpec` is a custom message; its nanosecond comment contains an inconsistent upper-bound expression. Preserve values, and obtain the exact clock/synchronization contract before timestamp fusion. Foot-force integers in the GO reader are explicitly treated as uncalibrated values, not automatically newtons. [Readers](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_low_state.cpp), [motion/time schemas](https://github.com/unitreerobotics/unitree_ros2/tree/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/cyclonedds_ws/src/unitree/)

Additional defined resources include GO audio/video byte payloads, LiDAR status, height maps, UWB state/switch, motor sequences, path points, legacy `Req`/`Res` and `SportModeCmd`; HG hand commands/state, pressure arrays, BMS and mainboard state. Their presence supplies types, not an assurance of active publishers, codec, units, sensor calibration or service entitlement on every robot. Use the exact message inventory in [the pinned interface directory](https://github.com/unitreerobotics/unitree_ros2/tree/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/cyclonedds_ws/src/unitree/). Do not confuse legacy GO `Req`/`Res` with the structured `unitree_api` request/response contract.

### SDK2 interoperability is conditional <a href="#sdk2-interoperability-is-conditional" id="sdk2-interoperability-is-conditional"></a>

DDS interoperability requires matching topic/domain/interface plus compatible serialized type names, field order, primitive types, array bounds and QoS. Installing SDK2 is not a substitute for compiling the ROS message types. Conversely, using the ROS packages does not prove the current SDK2 binary and robot firmware share an identical schema.

The v0.3.0 changelog explicitly changes `HandCmd`, `HandState` and `PressSensorState` to align with SDK2. Treat older generated hand types as potentially incompatible and rebuild the dependent workspace after reviewing changes. The ROS message packages still report `0.0.0`, so compare commits and source files. A concrete discrepancy remains at the reviewed pins: ROS GO `LowState.msg` declares `temperature_ntc1/2` as `int8`, while the inspected SDK2 GO header uses `uint8_t`. ## Getting started <a href="#getting-started" id="getting-started"></a>

### Prerequisites and stop conditions <a href="#prerequisites-and-stop-conditions" id="prerequisites-and-stop-conditions"></a>

There are two checkpoints. The first requires only Python 3 and the pinned text snapshot/checkout; it does not import ROS or vendor code. The second is a **subscriber-only hardware recipe**, blocked until the canonical robot guide establishes the purchased option, firmware/message pairing, network settings and stop controls. No motion publisher, API request client, mode-release client or vendor example is needed for either checkpoint.

### 1. First result: offline message-family inspection <a href="#id-1-first-result-offline-message-family-inspection" id="id-1-first-result-offline-message-family-inspection"></a>

1. Obtain the pinned source snapshot without running its setup scripts. Identify the directory containing `cyclonedds_ws/src/unitree`. The paths below assume an existing `~/unitree_ros2` checkout at the reviewed commit.
2. Keep robot data connections unused. Run this original text-only Python inspection; it opens `.msg` files as data, and starts no ROS or DDS participant.
3. Check both layout capacities and the absence of a supplied `unitree_h1` directory. If any assertion fails, stop and identify the actual checkout/version rather than adapting a decoder by guesswork.

```python
from pathlib import Path
root = Path.home() / "unitree_ros2" / "cyclonedds_ws" / "src" / "unitree"
for family, slots in (("unitree_go", 20), ("unitree_hg", 35)):
    fields = {}
    for line in (root / family / "msg" / "LowState.msg").read_text().splitlines():
        line = line.split("#", 1)[0].strip()
        if line:
            kind, name = line.split()
            fields[name] = kind
    assert fields["motor_state"] == f"MotorState[{slots}]"
    print(f"{family}: LowState motor_state slots = {slots}")
assert not (root / "unitree_h1").exists()
print("unitree_h1: not supplied in this snapshot")
```

**Expected result:** three descriptive lines with GO 20, HG 35 and `unitree_h1` not supplied. These are schema facts, not robot observations. The bundle's original offline checker additionally inspected the four reader source files and found subscription creation without application publisher creation; that text scan was executed successfully. It is not C++ compilation, a formal call-graph proof or a DDS test.

### 2. Conditional first robot result: one state sample, subscriber only <a href="#id-2-conditional-first-robot-result-one-state-sample-subscriber-only" id="id-2-conditional-first-robot-result-one-state-sample-subscriber-only"></a>

Do not proceed until the unresolved firmware/option checks above are closed for the actual robot. The following Humble CLI recipe is specified for later use; it was **not run**. ROS inspection commands participate in network discovery even though they issue no application actuator commands.

1. Prepare the interface-only Humble environment from the preceding section with data connections still unused. Verify the selected `.msg` files against the pinned source before any robot-facing operation.
2. Have the operator identify the robot, confirm its firmware and schema family, record the physical stop method, and establish the dedicated Ethernet connection using the canonical robot guide. Apply the host network plan only after confirming the README's example address is appropriate for this robot.
3. In a fresh Humble shell, source only the matching interface overlay. Set Cyclone RMW, the confirmed robot domain (normally 0 in the cited examples) and XML with the actual Ethernet interface. Do not reuse the simulation domain/interface template unchanged. If a ROS CLI daemon is already running with other settings, stop that local daemon before rediscovery so stale middleware/domain state does not determine the result.
4. Discover topics and inspect the exact state endpoint. These are graph inspection actions, not commands to the robot:

```bash
ros2 topic list -t
ros2 topic info /lowstate --verbose
```

5. Select **one** of the following after inspecting the advertised type. For an identified GO-contract Go2/B2, use:

```bash
timeout 10s ros2 topic echo /lowstate unitree_go/msg/LowState --once --qos-reliability best_effort --qos-durability volatile
```

For an identified HG-contract G1/H1-2, use instead:

```bash
timeout 10s ros2 topic echo /lowstate unitree_hg/msg/LowState --once --qos-reliability best_effort --qos-durability volatile
```

The Humble CLI source supports explicit message type, `--once`, reliability and durability arguments. Best-effort/volatile is an initial state-observation choice, not a throughput or loss guarantee. Compare offered QoS with `topic info` if nothing arrives. `timeout` bounds a wait for a missing stream; it does not stop other controllers. [Humble echo implementation](https://github.com/ros2/ros2cli/blob/humble/ros2topic/ros2topic/verb/echo.py), [topic information](https://github.com/ros2/ros2cli/blob/humble/ros2topic/ros2topic/verb/info.py)

6. Preserve the advertised type, source commit, firmware identity, domain, Ethernet interface, package versions and captured sample with its acquisition time. If freshness matters, perform a second bounded subscription and compare the raw tick/state, without assigning an undocumented tick period.

**Expected result:** a decoded sample with GO's twenty or HG's thirty-five motor-state entries, an IMU block and tick, followed by normal completion after one received sample. Actual values depend on the robot; no fabricated position, voltage, mode or time value is prescribed. A timeout, type error, absent endpoint or multiple incompatible types is a failed checkpoint. Leave the command path unused and diagnose the state path.

For a correctly identified GO robot whose motion service is already publishing state, `/lf/sportmodestate` is the default in `read_motion_state.cpp`; `/sportmodestate` is the high-frequency alternative. It can be inspected with the same bounded echo pattern using `unitree_go/msg/SportModeState` and the actually advertised topic. No state-publication frequency is guaranteed by this guide. Do not start or stop a motion service merely to make this diagnostic appear. [Motion reader](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_motion_state.cpp)

### Control examples are a separate operation <a href="#control-examples-are-a-separate-operation" id="control-examples-are-a-separate-operation"></a>

The G1 low-level example starts a periodic command timer and moves toward a zero posture before later ankle/wrist trajectories. Go2 sport/stand clients, H1-2/H2 low-level examples, arm SDK, Dex3 and mode-switch clients likewise belong to control work. Their names may sound like connectivity checks, but they can command actuators or alter control ownership. They are not first-result commands here. A control session requires exact active joints, mode semantics, gains, command deadlines, stop behavior, restraint and an explicit single-writer handover. [G1 example](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/g1/lowlevel/g1_low_level_example.cpp), [example target list](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/CMakeLists.txt)

The CRC helpers also must not be promoted into a generic publisher recipe. GO and HG helpers construct different raw layouts. At this pin the HG helper copies only four bytes from a four-word reserve array; behavior for nonzero later reserve words requires review. No checksum test or firmware acceptance test was performed. This source observation is another reason to keep publishing outside the state-acquisition procedure. [CRC sources](https://github.com/unitreerobotics/unitree_ros2/tree/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/common/)

## Troubleshooting and FAQs <a href="#troubleshooting-and-faqs" id="troubleshooting-and-faqs"></a>

### No Unitree topics appear <a href="#no-unitree-topics-appear" id="no-unitree-topics-appear"></a>

Check, in order: the identified Ethernet interface/link and approved address plan; whether Cyclone XML names a real interface; the selected ROS distribution and overlay; `RMW_IMPLEMENTATION`; the confirmed domain; and whether an older local CLI daemon was created under other settings. On a container host, inspect actual network isolation: the vendor Compose file uses host networking. Compare loopback/domain 1 for simulation with Ethernet/domain 0 for the cited real-robot examples. Do not disable security controls globally or scan unrelated networks to compensate for an unverified configuration. [Setup](https://github.com/unitreerobotics/unitree_ros2/tree/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88), [container](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/.devcontainer/docker-compose.yml), [domain distinction](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/readme.md)

### A topic is visible, but echo receives nothing <a href="#a-topic-is-visible-but-echo-receives-nothing" id="a-topic-is-visible-but-echo-receives-nothing"></a>

Discovery is not successful type/QoS/data exchange. Inspect the endpoint type and offered QoS, then ensure the exact interface package overlay is loaded. GO and HG can use the same ROS topic string `/lowstate` while carrying incompatible types. Keep the bounded best-effort/volatile reader and inspect errors. Check that the publisher is active for the confirmed firmware/service configuration. Do not send a motor command to test a missing state stream. [State schemas](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/cyclonedds_ws/src/unitree/unitree_go/msg/LowState.msg), [HG schema](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/cyclonedds_ws/src/unitree/unitree_hg/msg/LowState.msg), [Humble echo behavior](https://github.com/ros2/ros2cli/blob/humble/ros2topic/ros2topic/verb/echo.py)

### The HG reader shows only twelve motors <a href="#the-hg-reader-shows-only-twelve-motors" id="the-hg-reader-shows-only-twelve-motors"></a>

That is a limitation of `read_low_state_hg.cpp`: it allocates 35 motor-state slots but its log loop iterates twelve times. It does not prove that only twelve joints exist or that the remaining joints failed. Use a full-message bounded subscriber and the exact robot's active-joint map; do not replace the loop bound with 35 and assume all slots are valid actuators. [HG reader](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_low_state_hg.cpp)

### Which low-frequency state topic should be used? <a href="#which-low-frequency-state-topic-should-be-used" id="which-low-frequency-state-topic-should-be-used"></a>

Inspect the actual endpoint. The GO reader's active `HIGH_FREQ=true` path uses `lowstate`, but its inactive alternate literal is `hf/lowstate`, inconsistent with nearby low-frequency comments and the README's `lf/lowstate`. The HG alternate literal is `lf/lowstate`. The motion reader defaults to `lf/sportmodestate`. These are source observations, not a promise that every firmware publishes all variants. [GO reader](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_low_state.cpp), [HG reader](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_low_state_hg.cpp), [motion reader](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_motion_state.cpp)

### Why does a service client time out or fail to match a response? <a href="#why-does-a-service-client-time-out-or-fail-to-match-a-response" id="why-does-a-service-client-time-out-or-fail-to-match-a-response"></a>

The common client publishes a structured request with a generated identity and waits for a response carrying that identity, then checks the status code. It waits up to five seconds in the reviewed implementation. A timeout leaves execution outcome uncertain; it is not permission to retry a non-idempotent motion request. ROS executor scheduling and firmware API availability require independent validation. Keep initial diagnosis on state endpoints. [Base client](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/include/common/base_client.hpp)

### Can simulation use the same topics as a real robot? <a href="#can-simulation-use-the-same-topics-as-a-real-robot" id="can-simulation-use-the-same-topics-as-a-real-robot"></a>

Yes, some DDS contracts and topic names are intentionally shared. Therefore isolate by both interface and domain, not by adding a visual label in the simulator. The reviewed MuJoCo README recommends domain 1 and `lo`; its real-robot example uses domain 0. `setup_local.sh` alone does not change domain. Simulation success does not verify real-time deadlines, physical stop behavior, calibration or active joints. [Simulation documentation](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/readme.md)

There are concrete behavioral differences: the simulator retains `SportModeState` when a real robot's built-in motion service may no longer publish it, and its README uses `rt/wireless_controller`, while the ROS reader uses `/wirelesscontroller`. Do not assume the underscore and non-underscore names are aliases. Compare each producer/consumer's exact topic strings. The G1 secondary IMU stream described by the simulator is not automatically a standard `/imu` topic or a valid TF tree. [MuJoCo supported messages and joystick sections](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/readme.md), [wireless reader](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_wireless_controller.cpp)

### How does SDK2 `rt/lowstate` relate to ROS `/lowstate`? <a href="#how-does-sdk2-rtlowstate-relate-to-ros-lowstate" id="how-does-sdk2-rtlowstate-relate-to-ros-lowstate"></a>

Unitree's SDK2 examples use the DDS topic string `rt/lowstate`; the ROS examples use `lowstate` in the root namespace, displayed as `/lowstate`. Treat those as their respective API-level names, not as a reason to manually add `/rt/` to every ROS command. Preserve exact topic/type/namespace records when using remapping or a custom bridge. A bridge needs its own schema and name-mapping review. [SDK2 H1 subscriber](https://github.com/unitreerobotics/unitree_sdk2/blob/b7fec6020eb93d4c059a6edf19905e12a75a8d3d/example/h1/low_level/humanoid.hpp), [ROS readers](https://github.com/unitreerobotics/unitree_ros2/blob/668d1ec5a05d1c38d3306bdca7d59f2ba3581a88/example/src/src/read_low_state.cpp), [simulation ROS/SDK examples](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/readme.md)
