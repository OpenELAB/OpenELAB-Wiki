## Product overview <a href="#product-and-scope" id="product-and-scope"></a>

This guide covers the **2023 Raspberry Pi 4B myAGV**, not myAGV Jetson, Plus, Pro or a myCobot arm bundle. The workbook/original German product uses `MyAGV-2023-PI`; the current IO catalog spells it `MyAGV-2023-Pi`. The exact2023 Pi model, handle and variant resolve that capitalization difference. [Original store reference](https://openelab.de/products/elephant-robotics-myagv-rpi-roboter),[current IO product](https://openelab.io/products/elephant-robotics-myagv-rpi-robot-kit-mapping-autonomous-navigation),[official model manual](https://docs.elephantrobotics.com/docs/myagv_pi23_en/).

myAGV2023 Pi is a Mecanum mobile base with an integrated Pi, LiDAR, camera and lower-level motion controller. Start with the supplied Ubuntu 20.04 image and its matched firmware/SDK. Its documented mapping lane is **ROS 1 Noetic**. A generic desktop icon for ROS 2 does not establish compatible ROS 2 drivers for this exact2023 image.

## Applications

Use the platform for omnidirectional driving, Python/Blockly control, LiDAR SLAM, waypoint navigation and optional mobile-manipulation integration. Begin with stationary version/status reads, then short floor moves and a small named map. A robot arm, extra battery, 7-inch display, pump or depth camera is an accessory unless explicitly supplied in the ordered kit.

Payload and speed must be considered together with stopping distance, center of gravity and floor traction. A top-mounted arm changes the base's footprint and stability; the 5 kg published base payload does not qualify every raised-arm configuration. Use the official mounting drawings and a separate integrated-system check before carrying an arm or other load.

### Power and logic boundaries

Use the marked DC input and supplied adapter for charging. The auxiliary XT30 arm output is rated 12 V 5 A in the manual; it is not a generic 5 V peripheral supply and must not backfeed the base. The GPIO header is 3.3 V logic and includes a 3.3 V supply/GND. Never connect12 V, an arm supply or a motor directly to it. Use a suitable interface/driver for external loads; the manual's approximate GPIO-current discussion is not a recommended motor/relay drive rating.

The detailed header table identifiesGPIO17, 27, 22, 10, 9, 11, 18, 23, 24, 25, 8, 7 plus3.3 V/GND. A summary table repeatsGPIO10 where the detailed table givesGPIO18; use the detailed labeled drawing and actual board silkscreen before wiring. GPIO alternate functions can make a signal unavailable while a peripheral owns it. No new pin allocation is assumed here. [Electrical table and header](https://docs.elephantrobotics.com/docs/myagv_pi23_en/2-ProductFeature/2.4-ElectricalCharacteristicParameter.html).

Keep the factory lower-controller UART connection unchanged. On the 2023 Pi image, the documented Python serial port is **`/dev/ttyAMA2` at 115200bit/s**. This differs from a Jetson USB serial path. Close AGV\_UI, myBlockly, ROS base nodes and other serial applications before direct SDK access. A backup battery or pump uses its dedicated connection; do not parallel a replacement pack through GPIO or an improvised Y-cable.

## Getting started <a href="#getting-started" id="getting-started"></a>

### 1. Boot and inspect without driving

1. Inspect the battery, charging connection, free Mecanum rollers and attached accessories. Use a clear level floor and remove loose objects from the wheel area.
2. Use the supplied adapter to complete charging as instructed by the first-use manual, then boot and wait for the desktop. Inspect the actual pack/charge state rather than assuming runtime from its nominal capacity.
3. Connect a monitor or the supplied remote-access method. The system guide identifies the initial password as `Elephant`; verify the actual user/IP in the delivered desktop rather than guessing a Hiwonder hotspot/account.
4. Open AGV\_UI for the documented status check, record its version and close it before a Python or ROS serial session. The default hotspot name follows `ElephantRobotics_AP_XXXX`; its actual configured address/credentials belong to that image.
5. Record the image/SDK/firmware pairing above. Keep motor and navigation controls inactive until the status check passes.

\*\*Expected result: \*\*normal desktop startup, readable image/package versions and one selected serial owner. A boot failure is diagnosed with the official power-on/FAQ steps before replacing the system card. [First-use test](https://docs.elephantrobotics.com/docs/myagv_pi23_en/4-FirstInstallAndUse/4.3-PowerOnDetectionGuide.html),[system and remote access](https://docs.elephantrobotics.com/docs/myagv_pi23_en/5-BasicApplication/5.1-SystemInstructionManual.html).

### 2. Original version-aware stationary telemetry log

On the matched v1.2/4.0.0 environment, save `myagv_status.py` and run `python3 myagv_status.py` with no other application holding `/dev/ttyAMA2`. The script sends a firmware query and reads MCU telemetry; it makes no movement, LED, restore, gyro-calibration or auto-report-setting call.

```python
import json
import time
from importlib.metadata import version
from pymycobot.myagv import MyAgv

print('pymycobot=', version('pymycobot'))
if version('pymycobot') != '4.0.0':
    raise SystemExit('Use this example with the reviewed4.0.0 schema/environment')
agv = MyAgv('/dev/ttyAMA2', 115200)
try:
    firmware = agv.get_firmware_version()
    if firmware is None:
        raise RuntimeError('No firmware reply; inspect power/port/owner')
    print('firmware_reply_raw=', firmware)
    received = 0
    for index in range(5):
        data = agv.get_mcu_info()
        print(json.dumps({'sample': index, 'telemetry_raw': data}))
        if isinstance(data, list) and data:
            received += 1
        time.sleep(0.2)
    if received == 0:
        raise RuntimeError('No telemetry received; do not infer battery state')
finally:
    agv.close()
```

\*\*Expected result: \*\*the 4.0.0 package identity, a firmware reply and nonempty telemetry rows. Values are explicitly raw; the script does not misinterpret the old three-element API description. It opens/closes the serial connection using public4.0.0 methods. A query timeout does not justify calling `restore()` or enabling a drive routine.

### 3. Establish manual movement and stop behavior

Use one official controller at a time. In myBlockly, select myAGV2023 and the correct serial settings, inspect the generated Python and begin with a short low-speed move followed by stop. SDK speed values1–127 are controller units, not meters per second; the motion methods default to 5 seconds if timeout is omitted. Explicit duration matters.

The Python source's `restore()` is motor-stall recovery, not an ordinary stop. Inspect and remove a physical stall before recovery. For ROS keyboard control, `k` stops; i/comma move forward/back; j/l translate; u/o rotate. Keep the teleop terminal focused and verify stop before a longer run. [API](https://docs.elephantrobotics.com/docs/myagv_pi23_en/6-SDKDevelopment/6.1-ApplicationBasePython/6.1.2-API.html),[ROS control](https://docs.elephantrobotics.com/docs/myagv_pi23_en/6-SDKDevelopment/6.2-ApplicationBaseROS1/6.2.4-Basic_Control_Based_on_ROS.html).

### 4. ROS 1 feedback and a saved map

Open the supplied ROS 1 environment and confirm `ROS_DISTRO=noetic`. Start the base once:

```bash
roslaunch myagv_odometry myagv_active.launch
```

The course expects `myAGV initialized successful!` and LiDAR scanning messages. The reviewed Pi launch includes the YDLIDAR X2 driver, robot state publishers and an odometry/IMU filter. The newer image auto-starts LiDAR power; run the legacy `start_ydlidar.sh` only if it is actually off and the matched image calls for it. Inspect existing owners before restarting a driver. [Actual Pi launch](https://github.com/elephantrobotics/myagv_ros/blob/v1.2.0-pi/myagv_odometry/launch/myagv_active.launch).

In separate terminals, launch `myagv_navigation myagv_slam_laser.launch` and `myagv_teleop myagv_teleop.launch`. Drive a slow small closed loop and watch wall overlap. The course suggests0.2m/s linear and 0.4rad/s angular mapping settings; choose a smaller clear test envelope first. Save under a distinct name:

```bash
rosrun map_server map_saver -f ~/myagv_ros/src/myagv_navigation/map/bench_map
```

\*\*Expected result: \*\*`bench_map.pgm` and `bench_map.yaml` with valid resolution, origin and existing image path. Preserve both files and the robot/image configuration. [Gmapping workflow](https://docs.elephantrobotics.com/docs/myagv_pi23_en/6-SDKDevelopment/6.2-ApplicationBaseROS1/6.2.5-Real-time_Mapping_with_Gmapping.html).

### 5. Navigation, GUI development and extensions

Set the navigation launch's `map_file` to the saved YAML, then start `roslaunch myagv_navigation navigation_active.launch` with the base already running once. Initialize2D Pose Estimate so laser walls align with the map. Add one nearby2D Nav Goal with Loop off and start navigation. Inspect the planned path before allowing travel.

The official multi-goal panel has a specific cancel/resume behavior: Cancel stops the current goal; starting again can advance to the **next**goal rather than resuming the interrupted one. Reset clears the target list. Check the list before restarting and avoid surprise waypoint skips. [Navigation panel and pose settings](https://docs.elephantrobotics.com/docs/myagv_pi23_en/6-SDKDevelopment/6.2-ApplicationBaseROS1/6.2.6-Navigation-Map_Navigation.html).

### 5. Python API, ownership and state contracts

For the version-paired August2025 lane, the concrete class is `pymycobot.myagv.MyAgv(comport, baudrate=115200, timeout=0.1, debug=False)`, using `/dev/ttyAMA2` on the AGV Pi. Construction opens serial immediately. The helper uses pyserial's ordinary 8-bit/no-parity/one-stop defaults and deasserts RTS; the ROS implementation independently specifies 115200/8N1/no flow control. `timeout=0.1` is the serial read timeout; it is **not** the movement duration or an MCU watchdog. [Python class](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py); [serial helper](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagvapi.py); [ROS driver](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp).

Only one application should own this MCU port: direct Python, myBlockly, AGV\_UI or the ROS base driver. The Python object uses an internal mutex around one command transaction, but this does not coordinate multiple processes or two independently created objects. Before every `_merge` transaction the implementation clears both input and output buffers. Repeated “read” API calls therefore discard existing received data; they are not passive packet sniffing. `clear()` explicitly resets both buffers. `is_open()` reports the host port state; `close()` closes it and `open()` reopens it. Neither proves MCU health, and **close does not send stop**. Debug mode can write `python_debug.log` with rotating 100 MiB files; retain useful logs with version information. [Python](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py); [helper](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagvapi.py).

Speed is an unsigned controller-level magnitude, not m/s, degrees or a travel distance. Setter/movement methods usually return `None` immediately after host-side sending; that is not device acknowledgement. No supported independent firmware command-age timeout, physical emergency-stop category, torque-off or brake state is established by these sources. ### 6. Serial frame and complete v4 command reference

This is a reconstruction from the **actual source**, not a separate OEM-published complete protocol standard. A frame begins `FE FE`; the last byte is the low8 bits of the sum of every byte **after the two headers and before the checksum**. Multi-byte command codes are transmitted high byte then low byte (`01 0B`, for example). There is no length byte or terminator in the inspected command frames. The helper includes an unused CRC16 routine; these AGV commands use the additive8-bit checksum, not that CRC16. [Python encoder/parser](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py); [helper](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagvapi.py).

For all command rows, `b0,b1=FE,FE`, `b2=01`, `b3=opcode`, then parameters as below, then checksum. `u8` means one unsigned byte. Response rows describe only what the inspected getter consumes; they do not establish extra reserved fields or other firmware generations.

| Opcode    | API / purpose               | Outgoing parameters and total bytes         | Consumed response / effects                                             |
| --------- | --------------------------- | ------------------------------------------- | ----------------------------------------------------------------------- |
| `00`      | Restore stall               | b4=`01`; b5=sum; **6**                      | No reply requested; recovery changes fault/run state                    |
| `02`      | Set RGB/blink               | b4=mode1/2, b5=R, b6=G, b7=B; b8=sum; **9** | No reply requested; each color0…255                                     |
| `03`      | Firmware version            | No parameter; b4=sum; **5**                 | Reply matching b2/b3; b4 u8 divided by10; accepted reply at least6bytes |
| `07`      | Set gyro calibration enable | b4=state0/1; b5=sum; **6**                  | No reply requested; source docstring says saved over power loss         |
| `08`      | Get gyro enable             | No parameter; b4=sum; **5**                 | Matching reply b4 raw0/1                                                |
| `09`      | Get modified revision       | No parameter; b4=sum; **5**                 | Matching reply b4 rawu8                                                 |
| `0A`      | LED indication mode         | b4=0 charging/1DIY; b5=sum; **6**           | No reply requested                                                      |
| `0B`      | Set body motion             | b4=x, b5=y, b6=angular, b7=sum; **8**       | No reply requested;128 neutral each axis                                |
| `0C`      | Set automatic reporting     | b4=state0/1; b5=sum; **6**                  | No reply requested;1 enables stream                                     |
| `0D`      | Get automatic reporting     | No parameter; b4=sum; **5**                 | Matching reply b4 raw0/1                                                |
| No opcode | MCU telemetry read          | **No transmission**                         | Wait for FEFE +26or42 data bytes +checksum; total29or45                 |

For Python direction magnitude `s`, forward uses `(128+s,128,128)`, reverse `(128−s,128,128)`, left `(128,128+s,128)`, right `(128,128−s,128)`, clockwise `(128,128,128−s)`, counterclockwise `(128,128,128+s)`. The allowed s1…127 yields1…255 on the changing axis; stop is exactly `(128,128,128)`. This encoding does not establish acceleration or torque limits. [Python direction methods](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py).

#### v4 Python telemetry layout

Here `d0` is the first byte **after FEFE**, not a command opcode. A short packet has d0…d25; a long packet adds d26…d41. `i16BE` is a signed16-bit big-endian value. The source helper divides then rounds **every decoded numeric pair to two decimal places**, including nominal `/1000` fields. The table follows executed parser indices rather than the inconsistent index ranges in its docstring. [Parser](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py); [numeric helper](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagvapi.py).

| Data offsets                | Output list index | Actual v4 conversion                          | Physical interpretation / limitation                                                           |
| --------------------------- | ----------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| d0,d1,d2                    | 0,1,2             | Three rawu8 values                            | Documented as vx,vy/angular-related values, but parser leaves center128 and scale untouched    |
| d3–4,d5–6,d7–8              | 3,4,5             | `round(i16BE/100,2)`                          | Described as acceleration components; see ROS conflict below                                   |
| d9–10,d11–12,d13–14         | 6,7,8             | Same `/100`                                   | Described as angular-rate components; unit not independently established                       |
| d15                         | 9                 | Binary string, left-padded to at least6digits | Battery/adapter bit flags; `zfill(6)` does not truncate a set bit6/7                           |
| d16,d17                     | 10,11             | u8/10                                         | Main and backup battery volts                                                                  |
| d18–19,d20–21,d22–23,d24–25 | 12…15             | `round(i16BE/1000,2)`                         | Four fields; SDK docstring's battery-current index ranges do not unambiguously assign all four |
| d26–27,d28–29,d30–31        | 16…18, long only  | `round(i16BE/1000,2)`                         | Docstring describes roll/pitch/yaw; conflicts with ROS `/100` conversion                       |
| d32,d33                     | 19,20, long only  | Rawu8                                         | Docstring intended battery normal and MPU normal:1normal/0abnormal; verify matched MCU schema  |
| d34…37                      | 21…24, long only  | Four rawu8                                    | Intended four wheel stall states:1stalled/0normal                                              |
| d38…41                      | 25…28, long only  | Four rawu8                                    | Intended encoder states:1normal/0abnormal                                                      |

Thus the actual short return has **16 elements**, long **29**. It is not `[battery_flags,main_voltage,backup_voltage]`. For voltage use actual v4 positions10/11 only after confirming list shape, not old positions1/2. Intended status labels are documentation hints, not a validated firmware1.2 bit/physical-wheel ordering. No amperage scale is assigned to the four ambiguous fields. [Old API](https://docs.elephantrobotics.com/docs/myagv_pi23_en/6-SDKDevelopment/6.1-ApplicationBasePython/6.1.2-API.html); [actual v4 decoder](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py).

Battery bits from the older published battery description are: bit5 backup/battery2 inserted, bit4 main/battery1 inserted, bit3 adapter inserted, bit2 charging dock inserted, bit1 battery2 charge-light on, bit0 battery1 charge-light on. “Inserted” and “charge light on” are different states; the existence of a dock flag does not mean a dock is included. The published short API does not define higher bits. [Battery API](https://docs.elephantrobotics.com/docs/myagv_pi23_en/6-SDKDevelopment/6.1-ApplicationBasePython/6.1.2-API.html).

#### ROS decoder difference and synthetic arithmetic checks

The pinned ROS driver expects FEFE plus **43** bytes (42data+checksum), not the old27-byte comment. Its d0…2 decode as `(u8−128)×0.01` for body vx,vy and angular velocity. It decodes d3…8 as **unsigned little-endian**, subtracts10000 then multiplies0.001; d9…14 similarly but ×0.1. It decodes d26…31 as signed big-endian ×0.01 and treats yaw as degrees for quaternion conversion. Python v4 instead uses big-endian signed values `/100` and `/1000` as above. These are substantive differences in byte order, bias, scaling and output representation. The ROS angular-rate assignments also show no explicit degrees-to-radians conversion before populating `sensor_msgs/Imu`; their actual physical unit needs confirmation. Do not merge both decoders into a supposed universal packet definition. [ROS receive implementation](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp); [Python](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py).

The following are **original synthetic arithmetic examples, not device captures and not instructions to transmit**:

| Synthetic bytes / calculation        | Expected arithmetic result                         | What it demonstrates                                                   |
| ------------------------------------ | -------------------------------------------------- | ---------------------------------------------------------------------- |
| `FE FE 01 0B 80 80 80 8C`            | `(1+11+128+128+128) mod256 =140=0x8C`              | Neutral motion frame8bytes                                             |
| `FE FE 01 0B 8A 80 80 96`            | Sum406 mod256=150=0x96                             | Python forward magnitude10 changes x only                              |
| `FE FE 01 03 04`                     | 1+3=4                                              | Firmware query5bytes                                                   |
| `FE FE 01 07 01 09`                  | 1+7+1=9                                            | Gyro-state write framing, not a query                                  |
| `FE FE 01 0C 01 0E` / off ending`0D` | 1+12+1=14;1+12+0=13                                | Report enable/disable checksums differ                                 |
| Telemetry d16=`0x7E`                 | 126/10=12.6V                                       | Both implementations use the same main-voltage arithmetic              |
| Synthetic d3,d4=`27 10`              | Python:10000/100=100; ROS:(4135−10000)×.001=−5.865 | Endianness/bias disagreement cannot be resolved by relabeling a column |
| Synthetic d26,d27=`04 D2`            | Python:round(1234/1000,2)=1.23; ROS:1234×.01=12.34 | Angle scaling and precision differ                                     |
| Battery d15=`0x30`                   | six-bit string`110000`                             | Presence flags set does not set charging-light bits                    |
| Total packet lengths                 | 2+26+1=29;2+42+1=45                                | Header/data/checksum boundaries                                        |

A checksum verifies arithmetic consistency only. It does not prove firmware compatibility, state interpretation or safe motion. A later engineer must establish the MCU packet schema for the installed image before using these values for sensor fusion, current protection or calibration. No hardware-dependent claim is made by the arithmetic checks.

### 8. Base driver, ROS topics, transforms and command lifetime

`roslaunch myagv_odometry myagv_active.launch` starts the MCU driver, robot-description/state publishers, fixed transforms, EKF and YDLIDAR driver. **This launch writes hardware state:** initialization clears serial buffers, enables automatic telemetry and calls motor stall `restore()`. It is not a read-only discovery step. Clear obstructions and establish the controlled test area before launch. The destructor disables reporting, but the inspected source does not explicitly send neutral motion in its destructor. [Base launch](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/launch/myagv_active.launch); [driver](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp).

| Interface                       | Type / configuration                                                        | What to observe                                                                                               |
| ------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `cmd_vel` (normally `/cmd_vel`) | `geometry_msgs/Twist`, subscriber queue50                                   | Base uses `linear.x`, `linear.y`, `angular.z` only; other components ignored                                  |
| `odom`                          | `nav_msgs/Odometry`, publisher queue50; parent`odom`, child`base_footprint` | Position integrated from reported body velocity and IMU-derived yaw; not an absolute map position             |
| `imu`                           | `sensor_msgs/Imu`, queue20, frame`imu_link`                                 | Quaternion uses yaw only, roll/pitch forced0; verify units before quantitative fusion                         |
| `Voltage`                       | `std_msgs/Float32`, queue10                                                 | Main battery volts; capital V is part of the topic name                                                       |
| `voltage_backup`                | `std_msgs/Float32`, queue10                                                 | d17/10 only when d15 high nibble equals3; otherwise0. Zero can mean source gating, not measured empty battery |
| `scan`                          | Lidar scan consumed by mapping/localization/costmaps                        | Time-varying ranges and correct frame; not just a spinning motor                                              |
| Robot state/TF                  | URDF `myagv_urdf/urdf/myAGV.urdf`, joint/state publishers and EKF           | Consistent map→odom→base and sensor frames                                                                    |

The base subscriber stores the last Twist values without a timestamp or expiry check. The main loop is nominally100Hz but uses blocking serial reads; execute sends the stored command only after an accepted receive frame. Losing the keyboard, joystick or navigation publisher does not itself zero the stored command. There is no command mux or priority arbiter in this base subscriber. Use one intentional movement publisher at a time and establish an independent supervised stopping method; no MCU watchdog duration was verified. A UI close button, a disconnected SSH session and `rosnode kill` must not be described as verified hardware stops. [Subscriber/main loop](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGVSub.cpp); [driver execute](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp).

The ROS sender clamps x,y,w individually to −1…1, multiplies by100, converts to signed char and adds128. This is the source's command encoding, not a proof that 1m/s is within the published0.9m/s limit. Simultaneous axes are not bounded by a resultant-speed calculation. [ROS sender](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp).

The fixed transforms are, in the launch's `x y z yaw pitch roll` argument convention, metres/radians:

| Parent → child                 | Translation | Rotation yaw,pitch,roll | Publication period |
| ------------------------------ | ----------- | ----------------------- | ------------------ |
| `base_footprint`→`camera_link` | .13,0,.131  | 0,0,0                   | 50ms               |
| `base_footprint`→`imu_link`    | 0,0,0       | 0,3.14159,3.14159       | 50ms               |
| `base_footprint`→`laser_frame` | .065,0,.08  | 3.14159265,0,0          | 10ms               |

These are source mounting assumptions; moving a sensor requires measured transforms. The EKF uses output frame`odom`, base`base_footprint`, frequency30Hz, sensor\_timeout2s, odometry and IMU enabled, visual odometry disabled, and remaps `imu_data` to `imu`. Raw odometry TF broadcasting is commented out in favor of `robot_pose_ekf`. Do not add a competing broadcaster for the same transform. [Base launch](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/launch/myagv_active.launch); [driver](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp).

Raw odometry starts x/y/theta at zero each process run. Its yaw accumulator subtracts consecutive yaw values, drops changes strictly between−0.1 and0.1 degrees and does not visibly normalize a ±180-degree wrap. It integrates `dx=(vx cosθ−vy sinθ)dt`, `dy=(vx sinθ+vy cosθ)dt`. A restart changes this local origin; it does not redefine a saved map. Pose/twist covariance diagonals in source are approximately `[1e−9,1e−3,1e6,1e6,1e6,1e−9]`; IMU orientation/angular-rate diagonals are `[1e6,1e6,1e−6]`. These are configured confidence values, not measured sensor accuracy. No explicit linear-acceleration covariance is assigned in this code. [Odometry/IMU source](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp).

### 13. Calibration, mapping limits and diagnostic recovery

There are three different “zero” concepts: MCU gyro calibration-state enable; the ROS odometry origin at process start; and AMCL's initial pose in the selected saved map. `restore()` is stall recovery, not any of these. The reviewed manual does not supply a complete repeatable IMU bias routine, wheel-radius/track-width calibration API or verified closed-loop distance/angle command. The inspected base driver contains hardcoded conversions rather than a documented ROS wheel-scale parameter. Do not invent a `wheel_radius` parameter and imply the base consumes it. [SDK](https://raw.githubusercontent.com/elephantrobotics/pymycobot/v4.0.0/pymycobot/myagv.py); [driver](https://raw.githubusercontent.com/elephantrobotics/myagv_ros/v1.2.0-pi/myagv_odometry/src/myAGV.cpp); [FAQ](https://docs.elephantrobotics.com/docs/myagv_pi23_en/3-UserNotes/2_software.html).

A later calibration session should first record image/MCU/SDK/ROS versions, verify stationary telemetry and axes, then compare a short supervised physical displacement/rotation with odometry and map alignment. Record actual travelled distance and yaw, not merely requested time. Resolve the documented parser disagreement and yaw wrap/deadband before treating an error as a mechanical calibration failure. Moving a lidar/camera requires measured TF offsets. Camera intrinsics/hand-eye/marker size are separate from AMCL pose and from an arm's joint zero; no universal matrix is supplied here. These are engineering verification steps, not a claimed OEM calibration program already run.

### 15. Backup, SD image recovery and preservation

Preserve maps, custom launch/YAML, source changes, sensor/arm calibration records, network settings and a software/MCU version inventory before updates or image recovery. An original backup procedure for a later maintenance session is: stop movement and application writers; save the files above to separate storage; shut the host down cleanly; image the removable card with a trusted card-imaging tool's **read/backup** operation to a named file; verify the resulting file is readable and record its hash, card capacity and source version. Keep the original card untouched until a replacement has booted and the required configuration is present. This read-back procedure is engineering advice; the OEM page documents **writing** an image and does not provide a detailed backup verification recipe or official checksum. No card/device was read or written here. [OEM write procedure](https://docs.elephantrobotics.com/docs/myagv_pi23_en/8-FilesDownload/8.4-SystemInformation/8.4.2-Image_Burning.html).

For OEM image restoration, obtain the exact **Pi2023** compressed release, extract the `.img`, shut down/disconnect power, open only the indicated service access for the actual chassis revision, remove the TF card and connect it through a reader. The source pictures both v1.0/v2.0 access arrangements: the older sequence removes the pictured wheel to reach the card beside the Pi, whereas the later sequence marks four underside cover screws and accesses the card through that opening. Match the physical revision; avoid the adjacent ribbon/wiring and retain the wheel’s roller orientation on refitting. Those captions alone do not identify a Plus/Pro model. In Win32DiskImager choose the extracted image and the **actual removable-card device**; its example drive E is not universal. Write replaces existing card contents. Restore the card and enclosure, boot locally, then inspect `/etc/version`, account/network access and paired software/MCU before restoring custom data and testing sensors. Reimaging the Pi card and flashing the MCU are distinct operations. [Image burning with revision pictures](https://docs.elephantrobotics.com/docs/myagv_pi23_en/8-FilesDownload/8.4-SystemInformation/8.4.2-Image_Burning.html); [image table](https://docs.elephantrobotics.com/docs/myagv_pi23_en/8-FilesDownload/8.4-SystemInformation/8.4.1-System_Image.html).

Do not fabricate them. Do not restore an old entire configuration blindly over changed driver formats.
